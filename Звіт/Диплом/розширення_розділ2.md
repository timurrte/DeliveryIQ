## 2.2 Інформаційне забезпечення (розширена версія)

Інформаційне забезпечення системи охоплює сукупність даних, необхідних
для функціонування алгоритмів маршрутизації, та засоби їхньої організації,
зберігання й оновлення. Інформаційну модель розроблюваної підсистеми
доцільно розглянути на трьох рівнях абстракції: концептуальному (опис
сутностей предметної області), логічному (схема бази даних) і фізичному
(формати файлів зовнішнього обміну).

### 2.2.1 Сутності предметної області

Концептуальна модель будується навколо чотирьох ключових сутностей,
визначених у модулях `package_db.py` та `vrp_solver.py`:

– **Package (Посилка)** — фізичний об'єкт доставки, що має унікальний
ідентифікатор, адресу, вагу та поточний статус виконання замовлення.
Посилка є основною одиницею обліку і слугує первинним джерелом даних
для формування списку точок доставки.

– **DeliveryStop (Точка доставки)** — представлення геокодованої адреси
у форматі, придатному для алгоритмів маршрутизації. На відміну від
посилки, точка доставки додатково містить географічні координати,
часове вікно прийому товару та час обслуговування. Перетворення
*Package → DeliveryStop* відбувається на етапі підготовки даних до
оптимізації.

– **Vehicle (Транспортний засіб)** — атрибутивний опис одиниці
автопарку: ідентифікатор, режим переміщення (drive / bike / walk),
вантажна місткість та колір для візуалізації маршруту.

– **VehicleRoute (Маршрут ТЗ)** — результуюча сутність оптимізації:
послідовність точок доставки, призначених конкретному транспортному
засобу, з обчисленими часом та довжиною маршруту.

`PENDING` (очікує відправки) → `IN_TRANSIT` (передано на маршрут) →

автоматично при додаванні посилки у поточний маршрут оптимізатора;
перехід у `DELIVERED` виконується вручну оператором через
веб-інтерфейс.

### 2.2.2 Схема бази даних

Постійне зберігання інформації про замовлення реалізовано засобами
вбудованої у Python СКБД SQLite (версія 3.x). Вибір SQLite зумовлений
відсутністю потреби в окремому процесі-сервері, повною підтримкою
транзакцій ACID та крос-платформним характером файлу бази даних, що
дозволяє переносити стан системи між робочими станціями копіюванням
єдиного файлу `packages.db`.

Логічна схема бази складається з однієї таблиці `packages`, оператор
створення якої наведено нижче:

```sql
CREATE TABLE IF NOT EXISTS packages (
    id          TEXT    PRIMARY KEY,
    address     TEXT    NOT NULL,
    weight_kg   REAL    NOT NULL,
    status      TEXT    NOT NULL DEFAULT 'pending',
    created_at  TEXT    NOT NULL,
    lat         REAL,
    lon         REAL
);
```

Поле `id` зберігає 32-символьне шістнадцяткове представлення UUID
версії 4, що гарантує глобальну унікальність ідентифікатора посилки
без потреби в автоінкременті. Поле `status` приймає одне з трьох
значень множини `{'pending', 'in_transit', 'delivered'}`, що
відповідають елементам перерахування `DeliveryStatus`. Поле
`created_at` зберігається у форматі ISO 8601 у часовому поясі UTC;
такий вибір спрощує впорядкування записів та зіставлення часових
міток між різними машинами без додаткових перетворень. Координати
`lat`, `lon` допускають значення `NULL`, оскільки геокодування
адреси є асинхронним процесом і не завжди завершується успішно
(наприклад, при відсутності з'єднання з сервером Nominatim).

Доступ до даних інкапсульовано класом `PackageDB`, що реалізує
шаблон проєктування «Репозиторій» (Repository Pattern). Клас надає
наступний набір операцій CRUD:

– `add_package(address, weight, lat, lon)` — створення нового запису
з автоматичним призначенням UUID та поточного UTC-часу;

– `get_all()` / `get_by_status(status)` / `get_by_id(id)` —
вибірка з упорядкуванням за спаданням часу створення;

– `set_status(id, status)`, `set_weight(id, weight)`,
`set_coordinates(id, lat, lon)` — точкові оновлення окремих полів;

– `delete_package(id)` — фізичне видалення запису;

– `count_by_status()` — агрегаційний запит, що повертає кількість
посилок за кожним статусом для відображення у дашборді.

### 2.2.3 Формати зовнішнього обміну даними

Окрім реляційного сховища, система оперує даними у двох
неструктурованих форматах, що використовуються для обміну з
зовнішніми джерелами та для оптимізації продуктивності.

**Формат GraphML для кешу дорожньої мережі.** Завантажений з
OpenStreetMap граф вуличної мережі зберігається у локальному кеші у
форматі GraphML (XML-розширення для опису графів). Структура файлу
відповідає схемі бібліотеки OSMnx і містить три типи елементів:

– елементи `<node>` з атрибутами `id`, `y` (широта), `x` (довгота),
`street_count` (кількість інцидентних ребер);

– елементи `<edge>` з атрибутами `osmid`, `highway` (тип дороги),
`length` (геометрична довжина, м), `oneway` (булева ознака
односторонності), `travel_time` (час подолання ребра, с), а також
модальні теги `bicycle`, `motor_vehicle`, `foot`, `cycleway` тощо;

– елементи `<data key="…">` для метаданих графа в цілому: межі
завантаженої області (`bbox`), система координат (CRS), радіус
завантаження.

Кешування реалізовано через декоратор `@st.cache_resource`
фреймворку Streamlit; ключем кешу є кортеж `(lat, lon, radius)`
точки центра завантаження. Це дозволяє уникнути повторних звернень
до серверів Overpass API при незмінному депо та радіусі, що
скорочує час повторної оптимізації з 15–25 с до приблизно 0,5 с.

**Формат JSON для серіалізації результатів.** Результати
оптимізації передаються між серверним кодом і клієнтським браузером
через сесійний стан Streamlit у форматі JSON. Узагальнена структура
повідомлення про маршрут має вигляд:

```json
{
  "vehicle": {
    "name": "Транспорт 1",
    "mode": "drive",
    "capacity_kg": 500.0,
    "color": "#e41a1c"
  },
  "stops": [
    {"address": "...", "lat": 48.4647, "lon": 35.0462,
     "weight_kg": 2.5, "tw_open": 0, "tw_close": 86400}
  ],
  "tsp_route": [12345, 67890, 11122, 12345],
  "full_route": [12345, 13579, ..., 12345],
  "total_time_s": 1842.5,
  "total_dist_m": 18204.3
}
```

Поле `tsp_route` містить упорядкований перелік OSM-вузлів, які
відповідають точкам доставки, тоді як `full_route` — повна
послідовність вузлів проміжного дорожнього графа, відновлена
алгоритмом Дейкстри для кожного відрізка маршруту.

**Формат CSV для пакетного імпорту замовлень.** Для масового
завантаження адрес із зовнішніх систем (наприклад, ERP-систем
торговельних мереж) передбачено імпорт CSV-файлу з кодуванням
UTF-8 та комою як роздільник. Обов'язкові колонки: `address`
(текстова адреса), `weight_kg` (десяткова вага). Опціональні
колонки: `lat`, `lon` (передзадані координати), `tw_open_h`,
`tw_close_h` (часові вікна у годинах від півночі), `service_min`
(час обслуговування у хвилинах). Приклад рядка:

```csv
address;weight_kg;lat;lon;tw_open_h;tw_close_h;service_min
"просп. Гагаріна 8, Дніпро";2.50;48.4647;35.0462;9.0;18.0;5
```

### 2.2.4 Інформаційні потоки

Узагальнено цикл обробки інформації в системі складається з шести
етапів:

1. **Введення замовлення** — оператор вносить адресу та вагу у
веб-форму, дані потрапляють у таблицю `packages` зі статусом
`PENDING`;

2. **Геокодування** — модуль `Geocoder` робить запит до сервісу
Nominatim, отриманні координати записуються у поля `lat`, `lon`
відповідного запису;

3. **Формування заявки на оптимізацію** — оператор натискає
«Оптимізувати маршрути»; вибрані посилки конвертуються у список
об'єктів `DeliveryStop` і передаються до VRP-розв'язувача;

4. **Завантаження дорожньої мережі** — модуль `GraphBuilder`
читає GraphML з кешу або завантажує його з OSM, після чого
розраховує модальні графи з атрибутом `travel_time` на ребрах;

5. **Виконання оптимізації** — результат у форматі описаному вище
зберігається у сесійному стані Streamlit;

6. **Зміна статусів та архівація** — при підтвердженні доставки
оператор вручну переводить посилки у статус `DELIVERED`; усі
історичні записи залишаються у базі для подальшого аналізу.

## 2.3 Математичне забезпечення (розширена версія)

> математичне забезпечення)*

Математичне забезпечення розроблюваної інформаційної системи об'єднує
формальну постановку задачі маршрутизації транспортних засобів з
часовими вікнами та обмеженням вантажомісткості (CVRPTW), доведення
її обчислювальної складності, а також опис евристичних і
метаевристичних методів розв'язання, реалізованих у програмному
продукті.

### 2.3.1 Формальна постановка задачі CVRPTW

Транспортна мережа міста формалізується як зважений орієнтований
мультимодальний граф

$$G = (V, A), \quad V = \{0\} \cup C, \quad C = \{1, 2, \dots, n\}, \tag{2.1}$$

де $V$ — множина вузлів, $0$ — депо (склад), $C$ — множина клієнтів
(точок доставки), $A \subseteq V \times V$ — множина дуг.
Кожній дузі $(i,j) \in A$ ставиться у відповідність трійка

$$(d_{ij}, \, t_{ij}^m, \, \alpha_{ij}^m), \quad m \in M = \{\text{drive}, \text{bike}, \text{walk}\}, \tag{2.2}$$

де $d_{ij}$ — геометрична довжина ребра (м); $t_{ij}^m$ — час
подолання ребра $m$-м режимом, обчислений як $t_{ij}^m = d_{ij} /
v_m$ при $v_{\text{drive}} = 30$, $v_{\text{bike}} = 15$,
$v_{\text{walk}} = 5$ км/год; $\alpha_{ij}^m \in \{0, 1\}$ —
індикатор прохідності ребра для режиму $m$ з урахуванням
односторонності, заборон руху та типу покриття.

Кожен клієнт $i \in C$ характеризується кортежем атрибутів
$(q_i, \delta_i^-, \delta_i^+, s_i)$, де $q_i$ — маса замовлення;
$[\delta_i^-, \delta_i^+]$ — часове вікно, протягом якого клієнт
може прийняти товар; $s_i$ — тривалість обслуговування.

Автопарк $K = \{1, 2, \dots, |K|\}$ складається з транспортних
засобів, для кожного з яких задано $(Q_k, m_k)$ — вантажомісткість
та режим пересування.

Завданням задачі є побудова такої сукупності маршрутів $\{R_k\}_{k
\in K}$, що мінімізує цільову функцію та задовольняє всі обмеження
системи. Маршрут $R_k$ є впорядкованою послідовністю вузлів
$R_k = (0, r_k^1, r_k^2, \dots, r_k^{|R_k|}, 0)$, що починається і
закінчується у депо.

**Цільова функція.** Сумарна вартість розв'язку $F$ є зваженою
сумою двох компонент — загального часу руху та кількості
використаних транспортних засобів:

$$F = A \cdot T_{\text{total}} + B \cdot |K^*| \to \min, \tag{2.3}$$

$$T_{\text{total}} = \sum_{k \in K^*} \sum_{(i,j) \in R_k} t_{ij}^{m_k}, \tag{2.4}$$

де $K^* \subseteq K$ — підмножина транспортних засобів із
непорожніми маршрутами; $A$, $B$ — вагові коефіцієнти, що
визначають пріоритет компонент. У програмній реалізації прийнято
$A = 1.0$, $B = 0.0$ (мінімізація лише часу); зміна значень
$B > 0$ дозволяє надавати перевагу розв'язкам із меншою кількістю
задіяних машин.

Бінарні змінні задачі:

$$x_{ijk} = \begin{cases} 1, & \text{якщо ТЗ } k \text{ проходить дугою } (i,j) \\ 0, & \text{інакше} \end{cases} \tag{2.5}$$

$$y_k = \begin{cases} 1, & \text{якщо ТЗ } k \text{ задіяно у розв'язку} \\ 0, & \text{інакше} \end{cases} \tag{2.6}$$

**Обмеження задачі.**

1) Обмеження відвідування — кожен клієнт обслуговується рівно
одним транспортним засобом і рівно один раз:

$$\sum_{k \in K} \sum_{j \in V, j \neq i} x_{ijk} = 1, \quad \forall i \in C. \tag{2.7}$$

2) Збереження потоку — кількість вхідних і вихідних дуг через будь-
який вузол маршруту збігається:

$$\sum_{j \in V} x_{jik} = \sum_{j \in V} x_{ijk}, \quad \forall i \in V, \, \forall k \in K. \tag{2.8}$$

3) Початок і кінець маршруту в депо:

$$\sum_{j \in C} x_{0jk} \leq y_k, \quad \sum_{i \in C} x_{i0k} \leq y_k, \quad \forall k \in K. \tag{2.9}$$

4) Обмеження вантажомісткості:

$$\sum_{i \in C} q_i \sum_{j \in V} x_{ijk} \leq Q_k, \quad \forall k \in K. \tag{2.10}$$

5) Часові вікна. Нехай $\tau_i^k$ — момент початку обслуговування
клієнта $i$ транспортним засобом $k$. Тоді:

$$\delta_i^- \leq \tau_i^k \leq \delta_i^+, \quad \forall i \in C, \, \forall k \in K, \tag{2.11}$$

$$\tau_j^k \geq \tau_i^k + s_i + t_{ij}^{m_k} - M(1 - x_{ijk}), \quad \forall (i,j) \in A, \tag{2.12}$$

де $M$ — достатньо велика стала (Big-M), що гарантує виконання
обмеження лише для активних дуг ($x_{ijk} = 1$).

6) Сумісність ТЗ і ребра за режимом пересування:

$$x_{ijk} \leq \alpha_{ij}^{m_k}, \quad \forall (i,j) \in A, \, \forall k \in K. \tag{2.13}$$

7) Бінарність змінних:

$$x_{ijk}, y_k \in \{0, 1\}, \quad \forall i, j \in V, \, \forall k \in K. \tag{2.14}$$

### 2.3.2 Обчислювальна складність задачі

Задача CVRPTW належить до класу NP-складних. Доведення зводиться
до полінномного перетворення (поліноміальної редукції) класичної
задачі комівояжера TSP, NP-повнота якої встановлена Карпом у 1972 р.

**Твердження.** *Розв'язування задачі CVRPTW не менш складне, ніж
розв'язування TSP.*

**Обґрунтування.** Розглянемо обмежений випадок задачі CVRPTW з
такими параметрами: один транспортний засіб ($|K| = 1$),
необмежена вантажомісткість ($Q_1 = \infty$), необмежені часові
вікна ($\delta_i^- = 0$, $\delta_i^+ = \infty$ для всіх $i \in C$),
нульовий час обслуговування ($s_i = 0$) та єдиний режим
пересування. У такому формулюванні цільова функція (2.3)
зводиться до мінімізації загального часу руху одного ТЗ через
усі вершини $C$ з поверненням у депо $0$ — що є класичною задачею
комівояжера TSP. Оскільки TSP є NP-повною (Karp, 1972), то й
CVRPTW як її узагальнення є NP-складною. ∎

Кількість допустимих розв'язків задачі CVRPTW верхньо
обмежується величиною $n! \cdot |K|^n$, що для практично значущих
розмірностей ($n = 50$, $|K| = 5$) дає понад $10^{99}$
можливих маршрутів. Це робить методи повного перебору неефективними,
обґрунтовує застосування метаевристик і виправдовує вибір
генетичного алгоритму як основного методу розв'язання.

### 2.3.3 Кодування розв'язку

В реалізованому генетичному алгоритмі використовується непряме
кодування за схемою «giant tour»: хромосома є перестановкою
індексів клієнтів без явних маркерів розриву на маршрути:

$$\pi = (\pi_1, \pi_2, \dots, \pi_n), \quad \pi_i \in C, \quad \pi_i \neq \pi_j \text{ при } i \neq j. \tag{2.15}$$

Перетворення перестановки на сукупність допустимих маршрутів
відбувається процедурою Split-декодування (див. п. 2.3.5). Такий
підхід має дві ключові переваги: по-перше, оператори селекції,
схрещування та мутації застосовуються до простору перестановок,
що значно простіше за пряме оперування деревовидною структурою
маршрутів; по-друге, гарантується, що кожен клієнт зустрічається
у хромосомі рівно один раз, що автоматично виконує обмеження
відвідування (2.7).

### 2.3.4 Оператор схрещування OX (Order Crossover)

Класичний одноточковий або двоточковий кросовер для перестановок
непридатний, оскільки порушує властивість унікальності генів. У
розробленій системі застосовано оператор OX (Order Crossover),
запропонований Дейвісом у 1985 р. і теоретично обґрунтований
Олівером, Смітом і Голландом у 1987 р. для задач TSP.

Алгоритм OX-схрещування включає чотири кроки:

1) Випадково обираються дві позиції $i$ та $j$ ($0 \leq i \leq j <
n$), що утворюють інтервал-«ядро»;

2) Підпослідовність $\pi^{(1)}_i, \pi^{(1)}_{i+1}, \dots,
\pi^{(1)}_j$ першого батька копіюється в нащадка на ті ж позиції;

3) Решта позицій нащадка заповнюється генами другого батька в тому
порядку, в якому вони з'являються у $\pi^{(2)}$, починаючи з
позиції $j + 1$ і циклічно повертаючись до початку, з пропуском
генів, які вже наявні в нащадку;

4) Якщо $i \neq 0$, заповнення позицій $0, 1, \dots, i - 1$
здійснюється у тому ж порядку обходу.

**Приклад роботи OX-схрещування.** Нехай задано двох батьків
розмірності $n = 8$:

$$\pi^{(1)} = (1, 2, 3, 4, 5, 6, 7, 8),$$
$$\pi^{(2)} = (8, 5, 2, 1, 6, 3, 7, 4).$$

Випадково обрано межі ядра $i = 2$, $j = 4$. Сегмент $\pi^{(1)}$
з позиціями $[2, 4]$ — це $(3, 4, 5)$. Він копіюється в нащадка:

$$\pi^{(\text{child})} = (\_, \_, 3, 4, 5, \_, \_, \_).$$

Решта позицій заповнюється з $\pi^{(2)}$, починаючи з позиції $5$.
Послідовність $\pi^{(2)}$ у циклічному порядку, починаючи з
позиції $5$, така: $3, 7, 4, 8, 5, 2, 1, 6$. Гени $3$, $4$, $5$
вже наявні в нащадку — пропускаємо їх. Залишаються $7, 8, 2, 1, 6$.
Заповнюємо позиції нащадка у порядку $5, 6, 7, 0, 1$:

$$\pi^{(\text{child})} = (2, 1, 3, 4, 5, 7, 8, 6).$$

Отриманий нащадок є коректною перестановкою, успадковує
відносний порядок генів від другого батька і збереже структуру
підмаршруту з першого батька, що сприяє передаванню «корисних
генетичних блоків» між поколіннями. У реалізації операція виконується
з імовірністю $P_c = 0{,}85$.

### 2.3.5 Split-декодер

Декодер відіграє ключову роль у схемі «giant tour»: він
перетворює абстрактну перестановку на конкретний набір допустимих
маршрутів. У розробленій системі реалізовано жадібний варіант
Split-декодера, який, послідовно проходячи хромосому, додає
кожного наступного клієнта до поточного маршруту, поки виконуються
обмеження (2.10) і (2.11). При порушенні будь-якого обмеження
поточний маршрут закривається поверненням у депо, починається
новий маршрут на наступному вільному транспортному засобі.

Псевдокод декодера наведено нижче:

```
ВХІД:  π — перестановка індексів клієнтів
       K — список доступних транспортних засобів
       0 — індекс депо
ВИХІД: R — список маршрутів, кожен з яких послідовність вузлів
       U — список нерозподілених клієнтів

R ← ∅,  U ← ∅,  k ← 1
r ← (0),  Q ← 0,  τ ← δ_0^-

ДЛЯ кожного c ∈ π:
    i ← останній клієнт маршруту r (або 0, якщо порожній)
    Δt ← t_{i,c}^{m_k}              # час на дорогу
    arrival ← τ + service(i) + Δt    # момент прибуття
    start    ← max(arrival, δ_c^-)   # початок обслуговування
    feasible ← (Q + q_c ≤ Q_k) ∧ (start ≤ δ_c^+) ∧ (α_{i,c}^{m_k} = 1)

    ЯКЩО feasible ТО
        r ← r + (c)
        Q ← Q + q_c
        τ ← start
    ІНАКШЕ
        r ← r + (0)               # закрити маршрут
        R ← R + (r)
        k ← k + 1
        ЯКЩО k > |K| ТО
            U ← U + (c)            # клієнт не вмістився
            CONTINUE
        r ← (0, c)                 # новий маршрут
        Q ← q_c
        τ ← max(t_{0,c}^{m_k}, δ_c^-)

ЯКЩО r ≠ (0) ТО R ← R + (r + (0))
ПОВЕРНУТИ (R, U)
```

Обчислювальна складність декодера лінійна за розмірністю
хромосоми: $O(n)$. Це дозволяє виконувати оцінку придатності для
популяції з 50 особин і 150 поколінь за прийнятний час навіть на
задачах із кількома десятками клієнтів.

### 2.3.6 Оператор мутації та функція придатності

Для забезпечення генетичного різноманіття та запобігання
передчасній збіжності застосовується оператор swap-мутації: з
імовірністю $P_m = 0{,}15$ у хромосомі випадково обираються дві
позиції, і гени на цих позиціях переставляються місцями.

Функція придатності особини обчислюється на основі результату
Split-декодування:

$$f(\pi) = A \cdot T_{\text{total}}(\pi) + B \cdot |K^*(\pi)| + \Lambda \cdot |U(\pi)|, \tag{2.16}$$

де $T_{\text{total}}(\pi)$, $|K^*(\pi)|$ — компоненти цільової
функції (2.3) для декодованого розв'язку; $|U(\pi)|$ — кількість
нерозподілених клієнтів; $\Lambda = 10^6$ — штрафний коефіцієнт,
що робить будь-який неповний розв'язок гірше за будь-який повний.
Це гарантує, що еволюційний пошук пріоритезує повноту доставки
над компактністю маршруту.

### 2.3.7 Параметри генетичного алгоритму та критерій зупинки

Загальні параметри метаевристичного процесу, підібрані за
результатами попередніх обчислювальних експериментів, наведено у
таблиці 2.2.

**Таблиця 2.2 — Параметри генетичного алгоритму**

| Параметр | Позначення | Значення | Призначення |
|---|---|---|---|
| Розмір популяції | $N_{\text{pop}}$ | 50 | кількість особин у поколінні |
| Кількість поколінь | $N_{\text{gen}}$ | 150 | критерій зупинки |
| Імовірність схрещування | $P_c$ | 0,85 | частота застосування OX |
| Імовірність мутації | $P_m$ | 0,15 | частота swap-мутації |
| Розмір еліти | $N_e$ | 2 | особин копіюються без змін |
| Розмір турніру | $N_t$ | 3 | кандидатів у селекції |
| Штраф за нерозподілений вузол | $\Lambda$ | $10^6$ | пріоритет повноти доставки |

Критерієм зупинки служить вичерпання заданого ліміту поколінь
$N_{\text{gen}}$. Альтернативними критеріями (не використовуються
у поточній реалізації, але передбачені архітектурою для майбутніх
розширень) можуть бути: відсутність покращення цільової функції
протягом заданого числа послідовних поколінь, перевищення
загального часу обчислень або досягнення цільового значення $F$
відносно нижньої оцінки.

### 2.3.8 Початкова популяція з «теплим стартом»

Якість збіжності генетичного алгоритму значною мірою визначається
якістю початкової популяції. У розробленій системі застосовано
гібридну схему: одна особина створюється детермінованим
конструктивним алгоритмом найближчого сусіда (Nearest Neighbour),
а решта $N_{\text{pop}} - 1$ особин формуються незалежними
випадковими перестановками. Перша особина гарантує наявність
«розумного» базового розв'язку вже на нульовому поколінні, тоді
як випадкові особини забезпечують генетичне різноманіття для
дослідження простору розв'язків.

Така стратегія «теплого старту» (warm start) у поєднанні з
елітизмом гарантує монотонне (нестроге) покращення найкращого
розв'язку від покоління до покоління і пришвидшує практичну
збіжність на 20–30 % порівняно з виключно випадковою ініціалізацією.
